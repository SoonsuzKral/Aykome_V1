## 2) Token Gerçek İsim Sorunu — GERÇEK KÖK NEDEN + ÇÖZÜM

### 2.1 İlk deneme (Windows Cert Store) — YETERSİZ ÇIKTI
`aykome-e-imza/src/pkcs11/scanner.js::detectViaWindowsCertStore()` (PowerShell
ile `Cert:\CurrentUser\My` okuyor, PIN istemiyor) `main.js`'e bağlandı. **Canlı
testte BOŞ çıktı** — `Get-ChildItem Cert:\CurrentUser\My` sadece bir
"localhost" sertifikası gösterdi. Kök neden: AKIS/E-Tuğra sertifikaları bu
makinede SADECE PKCS11 middleware (`akisp11.dll`) üzerinden erişilebiliyor,
Windows CSP/Minidriver kurulu değil → sertifika CAPI/CNG deposuna hiç yansımıyor.

### 2.2 GERÇEK ÇÖZÜM — PKCS11 PIN'siz sertifika okuma
**Kanıtlandı:** `CKO_CERTIFICATE` nesneleri PKCS#11 standardında **public**
veridir (özel anahtar değildir). Terminal testi:
```
Pkcs11Bridge.exe C:\Windows\System32\akisp11.dll cert 00
→ WARN LoginSkipped: 0x000000A0  (yanlış/boş PIN, login başarısız)
→ CERT_DER 3082055a...  (AMA sertifika DER verisi GELDİ!)
→ CERT_OK
```
Hex içinde `41484D4554204B41414E204B4152415441C59E` = "AHMET KAAN KARATAŞ" (UTF-8).

**Değişiklikler:**
- `aykome-e-imza/x64-worker/Pkcs11Bridge.cs` (Windows, gerçek kullanılan) —
  "cert" komutunda `C_Login` başarısız olsa da (`rv != CKR_OK`) sertifika
  aramaya **devam eder** (sadece `cmd != "cert"` ise hâlâ hata verip çıkar —
  "sign" için login ZORUNLU kalır, imzalama güvenliği değişmedi).
  **Yeniden derlendi:** `csc.exe /nologo /optimize /out:Pkcs11Bridge.exe
  Pkcs11Bridge.cs` (`.NET Framework 4.0.30319` derleyicisi,
  `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`).
  **Yedek:** `Pkcs11Bridge.exe.bak4` (değişiklik öncesi hali).
- `aykome-e-imza/x64-worker/pkcs11-bridge.c` (Mac/Linux, bu makinede
  derlenmiyor ama tutarlılık için) — aynı mantık uygulandı.
- `aykome-e-imza/main.js` — yeni `tryReadCertViaPkcs11NoPin(libraryPath)`
  fonksiyonu: `BridgeWorker.getCertificate('', null)` (boş PIN) + `cert-utils.js
  ::parseCertificate()` ile CN çıkarır. `resolveTokenStatus()` artık ÖNCE bunu
  dener, olmazsa Windows Cert Store'a düşer (fallback korunur).

**Kullanıcı doğrulaması (ekran görüntüsü ile):** Kamu SM takılıyken panel
gerçekten **"MUSTAFA KEMAL KARATAŞ ✅ AKTİF"** gösterdi (Sertifika Seri:
`00c75e89144ba1bb`). Sorun kapandı.

### 2.3 İkinci bug — kart ÇIKARILINCA hâlâ "Algılandı" gösteriyordu
**Kök neden:** `scanner.js::detectWithPkcs11()` SADECE `fs.existsSync(dllPath)`
kontrolü yapıyor — sürücü kurulunca dosya HER ZAMAN durur, kart takılı olsun
olmasın. Gerçek fiziksel varlık kontrolü hiç yapılmıyordu.

**Çözüm — `main.js::checkRealSlotPresence(libraryPath)`:**
`BridgeWorker.listTokens()` (`Pkcs11Bridge.exe list` → `C_GetSlotList
(tokenPresent=TRUE)`, PIN istemez) ile gerçek slot sayısını kontrol eder.
`slots === 0` → kart fiziksel olarak yok → `durum: 'yok'` döner (placeholder
YERİNE). `resolveTokenStatus()` içine entegre edildi, `realCertCache`
(8 saniyelik) önbellek artık `{ slotPresent, certResult }` şeklini tutuyor.

**Not:** Bu düzeltme kullanıcı tarafından henüz "kartı çıkar, ekranı izle"
şeklinde canlı doğrulanmadı (kod mantığı sağlam, ama teyit gerekiyor).

**Değişen dosyalar:** `aykome-e-imza/main.js`,
`aykome-e-imza/x64-worker/Pkcs11Bridge.cs` (+ yeniden derlendi),
`aykome-e-imza/x64-worker/pkcs11-bridge.c`.

## 5) İkinci Tur Kullanıcı Geri Bildirimi (aynı gün, devam) — 2 Bug

### 5.1 BUG (regresyon) — Yeni PDF viewer 403 "Erişim Engellendi" veriyordu
**Kök neden:** `_signed_document_upload.blade.php`'deki
`route('admin.applications.module-document', [...])` çağrısı **absolute** URL
üretiyor (`http://127.0.0.1:8001/admin/applications/...`) — ama benim §4.4'te
yazdığım güvenlik kontrolü SADECE `/` ile başlayan (relative) URL'leri kabul
ediyordu. Absolute URL "http" ile başladığı için anında 403'e düşüyordu.

**Çözüm — `routes/admin.php::pdf-viewer`:** Artık `$url` `http(s)://` ile
başlıyorsa önce `parse_url()` edilir, **host kendi sunucumuzla eşleşiyorsa**
(`$request->getHttpHost()`) path+query kısmına indirilir, eşleşmiyorsa 403
(open redirect önlemi burada devam ediyor). Eşleşen relative path zaten
eskisi gibi prefix kontrolünden geçiyor.

veriyor. `fetch()` bir XHR/fetch tipi istektir — indirme yöneticilerinin
navigasyon/sub_frame filtresine TAKILMAZ (yaygın, bilinen bir çözüm deseni).
Fetch başarısız olursa (eski tarayıcı vb.) eskisi gibi doğrudan iframe'e
düşülüyor (fallback).

### 12.1 BUG — A4 kağıt boyutuna uymuyor, taşıyordu
**Kanıt:** Ekran görüntüsü — içe aktarılan Üst Yazı'da tepede dev boşluk +
boş bir “kutu” (Word'ün metin kutusu/çerçeve kalıntısı).

**Kök neden:** `PhpWord`'ün HTML çıktısı kendi mutlak konumlandırma
(`position/top/left`), sabit pt/px genişlik-yükseklik ve çok sayıda boş
(`&nbsp;`) paragraf içeriyor — bunlar A4 container'ın akışkan (fluid)
tasarımıyla çakışıp boşluk/taşma yaratıyordu.

**Çözüm — `DocumentTemplateService::sanitizeWordImportHtml()` (YENİ):**
`importWordToHtml()` artık bu adımı zincire ekliyor:
1. Mutlak konum (`position/top/left/right/bottom/z-index`) + yüzde-olmayan
   `width` + resim dışı `height` stilleri temizlenir.
2. Art arda 2+ boş paragraf tek paragrafa indirilir; içeriksiz `div`/`table`
   (Word'ün dönüştüremediği metin kutusu artıkları) tamamen silinir.
   **Önemli düzeltme (test sırasında bulundu):** Word'ün boş paragrafları
ASCII boşluk değil `&nbsp;` (U+00A0) içeriyor — düz `trim()` bunu
YAKALAMIYORDU, önce nbsp temizlenip sonra trim edilecek şekilde düzeltildi.
3. Cover_letter/on_kazi dışındaki tiplerde resimlere `max-width:100%`
   zorlanır (taşmasın).
**Doğrulandı:** Gerçek PhpWord test belgesiyle (resim + 3x boş paragraf)
çalıştırıldı, 3 boş paragraf → 1'e indi, mutlak konum kalıntıları gitti.

### 12.2 SORU/RİSK — E-imza sonrası 5070 metni + Belge Doğrulama Kodu kaybolur mu?
Kullanıcı sordu: Word ile yüklenen belge e-imzalandığında “5070 sayılı ...
